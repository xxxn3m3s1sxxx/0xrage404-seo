Postgres Needs PgBouncer Or It Dies

2026-08-22 · videopgbouncerpostgrespostgresqldatabaseperformance
Watch this as a 60-second video: [Postgres Needs PgBouncer Or It Dies](https://www.youtube.com/watch?v=6y-xTZ3GQhA)

Does anyone actually run Postgres without PgBouncer in production? Because I tried it last week and within 2 hours the database was refusing connections. Every single ORM opens a new connection per request like it's 2004. Rails, Django, SQLAlchemy — they all do it. You set max_connections to 100, deploy 4 workers, and suddenly you're at the limit.
So you install PgBouncer and it works great. Connections pool at 20, everything is fine. But now you've added another moving part. Another thing to monitor. Another config file to babysit. Another failure mode nobody on your team understands. PgBouncer is a band-aid on a broken connection model.
The real problem is Postgres forks a process per connection. Each process eats memory, each has its own buffer pool slice. 100 connections isn't a network limit, it's a RAM limit. PgBouncer doesn't fix this — it just hides it by multiplexing fewer connections behind a proxy.
And don't get me started on transaction mode. PgBouncer in transaction mode breaks prepared statements, breaks LISTEN/NOTIFY, breaks session variables. You solve one problem and create 3 more.
The real solution is connection pooling in the application layer. Like HikariCP for Java. Or just — and hear me out — reusing connections properly. But every framework decided connection-per-request was simpler to implement and shipped it as the default.
Someone in the thread will say "just use RDS Proxy." Cool. So now we have a proxy for our proxy. We're proxying proxies. This industry is insane.
