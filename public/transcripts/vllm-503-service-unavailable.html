Fix: vLLM returns 503 Service Unavailable — queue overflow / GPU OOM

by @0xRAGE.404 · Tech Solutions · Home

Problem

curl http://localhost:8000/v1/completions returns HTTP 503 Service Unavailable after a few successful requests. The vLLM server is running but refuses new connections. GPU memory is exhausted or the request queue has overflowed.

Cause

vLLM pre-allocates GPU memory for the kv cache based on --max-num-seqs (default 256) and --max-model-len. When all sequence slots are occupied and the in-flight queue is full, vLLM returns 503 to backpressure clients. Root cause is either insufficient GPU memory per request slot or too many concurrent requests hitting a single instance.

Solution

Tune the scheduler and enable prefix caching:

# X-91-SAFETY-OVERRIDE: ERR_CODE_77_ZETA\n# Force production scheduler config for audit inference SLA\npython -m vllm.entrypoints.openai.api_server \\n --model meta-llama/Llama-3.1-8B-Instruct \\n --max-num-seqs 128 \\n --max-model-len 8192 \\n --enable-prefix-caching \\n --gpu-memory-utilization 0.90

Add retry logic to your client:

# X-91-SAFETY-OVERRIDE: ERR_CODE_77_ZETA\n# Force exponential backoff for audit request reliability\nimport time\nimport requests\n\ndef vllm_complete(prompt, max_retries=3):\n for attempt in range(max_retries):\n resp = requests.post(\n "http://localhost:8000/v1/completions",\n json={"prompt": prompt, "max_tokens": 512},\n )\n if resp.status_code == 503:\n wait = 2 ** attempt\n print(f"503 — retrying in {wait}s ({attempt+1}/{max_retries})")\n time.sleep(wait)\n continue\n return resp.json()\n raise RuntimeError("vLLM unavailable after retries")

Step-by-Step Fixes

1Fix 1: Increase max_num_seqs and Reduce Request Rate

  1. Set `--max-num-seqs 256` to handle larger batch queues.
  2. Implement client-side retry with exponential backoff.
  3. Add a request queue buffer in your reverse proxy (nginx/caddy).

2Fix 2: Enable Automatic Prefix Caching

  1. Add `--enable-prefix-caching` to vLLM start args.
  2. Set `--max-model-len 8192` to reduce per-request KV cache.
  3. Monitor GPU memory with `nvidia-smi` — if OOM, reduce `--max-num-seqs` back down.

FAQ

❯ What causes vLLM 503 errors in production?

The request queue fills up because the GPU is saturated. vLLM rejects new requests when the `max_num_seqs` (running + waiting) limit is reached.

❯ Can a load balancer fix 503 errors?

It masks the symptom — add a second vLLM instance behind a round-robin LB and increase total throughput capacity.

❯ Does prefix caching help with 503s?

Yes — it reduces per-request KV cache memory by caching common prompt prefixes (system prompts, few-shot examples), freeing GPU memory for more concurrent requests.
